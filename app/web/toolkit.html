How one attack is processed

  1. Connect. An attacker (or the simulator) opens a TCP connection to a decoy port.
  2. Gate. Containment checks the kill switch, rate limit, concurrency cap and timeout.
  3. Open session. The current persona is assigned and the attacker's saved virtual filesystem is loaded.
  4. Choose strategy. The UCB1 bandit picks static, breadcrumbs, tarpit or rich, using the profile predicted from the IP's history.
  5. Interact. Each login, command or request is answered by the emulator (and the LLM when enabled).
  6. Analyse. Every event is tagged with ATT&CK, IOCs are extracted and queued for enrichment, the threat score is updated and the event is streamed live.
  7. Adapt. After 3 commands the profile is re-computed and the strategy may switch.
  8. Alert. High threat, canary use or ICS writes create alerts, delivered by webhook or syslog.
  9. Learn. On close, the engagement reward updates the bandit for (profile, strategy).
  10. Report. Analysts investigate in History and export reports, CSV and STIX/MISP.

How the project was analysed

The design follows a standard deception-engineering method:

Problem
Static honeypots are fingerprinted quickly and mostly collect automated noise.
Hypothesis
Adapting the response per attacker type increases engagement time and depth (commands), and lowers detection.
Control
The static arm is kept in the bandit as a built-in baseline for A/B comparison.
Measures
Avg duration, commands per session, detection rate, IOCs, MTTD (Area 9).
Threat model
Bots, scanners, script kiddies, skilled operators, ICS attackers.
Safety
Emulation only, no outbound from decoys, local binding by default, kill switch, audit log.
Evaluation
Attack Lab simulator → dashboard metrics → analysis report; then an isolated internet-facing pilot.
No API keys are required. The app works completely offline. Keys add enrichment and integrations; each one adds its host to the egress allow-list automatically. Keys are stored locally in your database and shown masked.
